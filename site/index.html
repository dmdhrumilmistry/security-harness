A review team, not a single prompt

One /indra request runs a pipeline of agents, each on the model its job needs. They coordinate through files, so every step is inspectable.

  1. ReconBuilds a code graph, the SBOM and known CVEs, and maps every entry point and trust boundary.
  2. HuntOne hunter per vulnerability class, in parallel, each loading its own knowledge base of 15.
  3. ChainCombines findings into escalations: an SSRF plus cloud metadata becomes credential theft.
  4. VerifyRefutes first, then proves exploitability from evidence, with a PoC, CVSS and a fix.
  5. ReportREADME, JSON, SARIF for code scanning, HTML and PDF.
  6. RememberRecords verified findings and false positives, so the next run starts ahead.

indra mem

Memory as a net of linked notes

Indra's net is an endless net with a jewel at every knot, each reflecting all the others. indra's memory works the same way: small Markdown notes joined by typed links like mitigated-by and instance-of.

  • Recall that follows links. Search finds a note; the graph brings in its mitigation, its false positives and its siblings, and says why.
  • Plain files. A vault is a folder that opens as-is in Obsidian and diffs cleanly in git.
  • Safe by design. Findings are remembered without evidence, payloads or secrets.
  • Connected. Import Obsidian, Notion exports and GitHub wikis; publish findings to Jira, Confluence, GitHub issues and Notion.
$ indra mem recall "django raw sql"
$ indra mem tree sqli
$ indra mem path "SSRF" "cloud credentials"

indra serve

Watch every agent at work

A local web console for indra and for any other agent harness. Launch a review and see each subagent it spawns, every tool call it makes, the permissions it was refused, and what it cost.

Locked down like a remote shell

Loopback only by default, a token on every call, DNS-rebinding and CSRF checks, no shell (the prompt is one argument) unless you start it with --shell, file access confined to the harness, and a strict Content-Security-Policy.

Configure everything from the browser

Runners, remote machines, workflows, presets, harnesses and capacity, on a Settings page. Every save is checked before it is written, applies at once, and keeps the comments in your indra.toml.

Steer agents from a terminal

indra attach follows an agent live in your own terminal: approve its tool requests, switch its mode or model, send it a message, or pivot it. With indra serve --shell the console also opens a real terminal in the browser, with your shell, Claude Code, or an agent's own session.

indra nodes · indra run

Orchestrate agents across machines

Run agents on this machine and on any machine you can SSH into. Chain them into workflows that run in dependency order, within each machine's capacity, with retries and cancel.

[[node]]
name         = "build-box"
ssh          = "ci@build-box.internal"
max_parallel = 2
targets      = ["/srv/api", "/srv/web"]

[[workflow.task]]
id     = "summary"
prompt = "Summarise tonight's reviews."
needs  = ["api", "web"]
  • No daemon, no open port. Remote machines are reached with your SSH keys and known hosts.
  • Nothing reaches a remote shell. The job travels as JSON; the remote runs only its own runners.
  • Stop means stop. Closing the session ends the agent's whole process tree on the remote.
  • Cron and CI ready. indra run nightly exits non-zero if any task failed.
